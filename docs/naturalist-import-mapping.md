# Импорт с naturalist.travel: маппинг, сопоставление и дополнение

Дополняет общую спецификацию [competitor-import-mapping.md](competitor-import-mapping.md).
Здесь только то, что специфично для источника «Натуралист».

Реализация: `src/backend/OnlyGlamps.Api/Services/NaturalistCrawler.cs`,
дополнение существующих карточек — `ImportService.EnrichAsync`.

---

## 1. Правовая и техническая рамка

`robots.txt` источника разрешает обход каталога: закрыты только
`?utm_source`, `?utm_campaign=`, `?amp`, `?ysclid=`, `?children=0` —
их краулер и так не запрашивает. User-Agent: `OnlyGlampsBot/1.0`,
между запросами пауза `delayMs` (1000–15000 мс, по умолчанию 1500).

**Не импортируем:**

| Поле источника | Почему |
|---|---|
| `description` / `og:description` | SEO-boilerplate с упоминанием бренда конкурента («…на сайте Натуралист») |
| `aggregateRating`, `scoreData` | отзывы и рейтинг — см. общую спеку |
| `telephone` | в JSON-LD это телефон площадки (ООО «НАТУРАЛИСТ»), а не объекта |
| `openingHours` | часы работы офиса площадки, к объекту не относятся |

Фото сохраняем как **внешние URL** источника, без скачивания бинарников —
так же, как это уже делают `VsaunahCrawler` и `MirturbazCrawler`. Это
расходится с §5 общей спеки («фото не импортируем»), но соответствует
фактическому поведению `ImportService` и нужно оператору, чтобы глазами
отсмотреть карточку перед публикацией.

## 2. Откуда берётся список объектов

**Не из sitemap.** `sitemap-iblock-1.xml` содержит 275 карточек и покрывает
каталог лишь частично: из 270 карточек категории `/bazy-otdykha/` в нём
всего 48. Остальные карты сайта (`chpy*.xml`, ~100 тыс. URL) — это
SEO-лендинги фильтров вида `/catalog/eko-oteli/u-ozera/s-rybalkoy/`.

По форме URL карточка и фильтр неразличимы: `/catalog/glempingi/` — фильтр,
`/catalog/tuchkovo-spa/` — объект. Эвристика по пути тут не работает.

Рабочий источник — **страницы категорий**: каждая отдаёт серверный массив
`window.mapItems` со ссылками на входящие карточки.

Категории двух сортов:

- **типовые** (`TypeCategories`, 20 шт.) — дают и карточку, и её тип;
- **региональные** (`DiscoveryCategories`, 50 шт., `v-moskovskoy-oblasti`
  и т.п.) — только обнаружение. Они делят каталог географически и достают
  объекты, не попавшие ни в одну типовую категорию. Тип для такого объекта
  берётся из типовой категории, если он и там есть, иначе из маркера
  в названии, иначе объект пропускается.

```
LoadTypeMapAsync()     → 70 категорий → CatalogIndex { TypeBySlug, AllSlugs }
FetchObjectUrlsAsync() → union(AllSlugs, sitemap) → /catalog/{slug}/
```

Индекс кэшируется на 6 часов и **только целиком**: если хоть одна категория
не прочиталась, кэш не пишется. Неполный индекс отравлял бы последующие
прогоны, и карточки массово уходили бы в «тип не определён».

### 2.1 Выдача фильтруется по доступности — снимок неполон всегда

Ссылки внутри `mapItems` приходят с параметрами
`?dateFrom=…&dateTo=…&guests=2`: источник показывает не весь каталог,
а то, что свободно на ближайшее окно дат под 2 гостей. Замеры на одной
и той же категории `glempingi`:

| Запрос | Карточек |
|---|---|
| без параметров, день 1 | 160 |
| без параметров, день 2 | 144 |
| `?guests=1` | 146 |
| `?guests=12` | 0 |

Отсюда два следствия:

1. Краулер ходит с `?guests=1` — это снимает отсечку по вместимости.
   (`?children=0` использовать нельзя: запрещён в `robots.txt` источника.)
2. **Один прогон физически не может увидеть весь каталог.** Покрытие
   набирается повторными прогонами: ключ дедупликации — `SourceUrl`,
   поэтому повторный запуск не плодит дубли, а добавляет новые карточки
   и дополняет уже известные. Регулярный прогон (например, раз в неделю)
   постепенно накрывает каталог целиком.

## 3. Маппинг полей

Данные карточки берутся из `<script type="application/ld+json">` с
`@type: Hotel` — на этом источнике он есть у каждой карточки.

| Источник | OnlyGlamps | Примечание |
|---|---|---|
| `name` | `Name` | HTML-decode, снятие кавычек |
| `address.streetAddress` | `Address` | снимается хвост «(67 км от Москвы)» |
| разбор `streetAddress` | `RegionId` | 1-я часть до запятой + алиасы |
| разбор `streetAddress` | `CityOrDistrictId` | населённый пункт, затем район |
| разбор `streetAddress` | `Settlement` | если город не сматчился — кладём сюда |
| `geo.latitude/longitude` | `Latitude/Longitude` | строки, валидируются по bbox РФ |
| `priceRange` | `Tariff` «Минимальная цена» | из «от 8 900 руб.» → `8900` |
| `amenityFeature[].name` | `ObjectAmenity` | `value` c `…/False` пропускается |
| `image` + `/upload/*` из DOM | `ObjectPhoto` | внешние URL, максимум 20 |
| DOM «N спальных мест» | `Capacity` | максимум по номерам, не сумма |
| — | `Status` | всегда `Draft` |

### 3.1 Вместимость

Карточка источника — это площадка с несколькими вариантами размещения
(«2 взрослых на основных местах», «3 спальных места»). Берём **максимум**
по номерам, а не сумму: `Capacity` у нас описывает один арендуемый объект.
Приоритет: «спальных мест» → «взрослых» → «гостей», потолок 50.
Если ничего не нашлось — объект пропускается (`Capacity` обязателен > 0).

### 3.2 Тип объекта

На карточке типа нет — в JSON-LD у всех `Hotel`. Тип берётся из категории:

| Категория источника | Наш `ObjectType.slug` |
|---|---|
| `glempingi`, `kempingi`, `tip-kemping`, `tip-safari-tent`, `tip-shatyer`, `tip-tipi`, `tip-yurta`, `tip-sfera` | `glempingi` |
| `gostevye-doma` | `gostevye-doma` |
| `bazy-otdykha` | `bazy-otdykha` |
| `zagorodnye-oteli`, `eko-oteli` | `park-oteli` |
| `tip-kottedzh`, `tip-a-frame`, `tip-barnkhauz`, `tip-dom-na-dereve`, `tip-dom-na-vode`, `tip-modulnyy-dom`, `tip-zerkalnyy-dom` | `kottedzhi` |

Порядок в `TypeCategories` значим — выигрывает первая совпавшая категория,
поэтому более конкретные типы идут раньше. Объект, не попавший ни в одну
категорию, определяется по маркерам в названии, а если и там пусто —
пропускается (тип не выдумываем).

### 3.3 Города и районы

**Новые `CityOrDistrict` не создаются** — это плодило бы индексируемые
маршруты (§7 общей спеки). Сейчас в БД 67 регионов и всего 68 городов,
поэтому «Рузский район» или «деревня Пантелеево» не матчатся ни на что.

Поведение в этом случае: объект уходит в первый город региона (fallback
`ImportService`), а нераспознанная локальность **сохраняется в `Settlement`**,
чтобы модератор видел фактическое расположение. Координаты при этом
импортируются точные, так что на карте объект стоит правильно.

> Чтобы объекты раскладывались по районам корректно, нужно отдельной
> задачей засидить `CityOrDistrict` для целевых регионов. Краулер
> подхватит их автоматически, без изменения кода.

## 4. Сопоставление с нашими объектами

Дедупликация — общая, из `ImportService.FindDuplicateAsync`:
`SourceUrl` → `Name`+город → `Name`+координаты ближе 500 м.

Дальше развилка:

- **не нашли** → `ImportAsync`: создаётся карточка в `Draft` с `SourceLink`;
- **нашли** → `EnrichAsync`: сравниваем и дополняем.

### 4.1 Правила дополнения

1. Заполняются **только пустые** поля. Ничего существующего не перезаписывается.
2. Расхождение (оба значения есть и различаются) не трогается, а возвращается
   в `enrichedSamples[].conflicts` — решает модератор.
3. Удобства и фото только **добавляются**, никогда не удаляются.
   Фото добавляются, лишь если своих нет вообще.
4. Флаги правил (`PetsAllowed` и т.п.) только поднимаются `false → true`:
   молчание источника не является доказательством запрета.
5. Тариф «от» добавляется, только если активных тарифов нет; иначе разница
   в цене уходит в `conflicts`.
6. **Пишем только в карточки системного импорт-пользователя со статусом
   `Draft`.** Карточку, которую забрал владелец или которая опубликована,
   краулер не трогает: возвращается `writable: false` и один только отчёт
   о том, что было бы заполнено, и в чём расхождения.

Флаг `allowOwned: true` снимает ограничение п.6 — только для осознанного
ручного прогона.

## 5. Запуск

```bash
# сухой прогон: ничего не пишем, смотрим что получилось бы
curl -X POST http://localhost:5001/api/admin/import/crawl/naturalist \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"offset":0,"limit":20,"dryRun":true,"delayMs":1500}'

# боевой прогон с дополнением существующих
curl -X POST http://localhost:5001/api/admin/import/crawl/naturalist \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"offset":0,"limit":50,"dryRun":false,"enrichExisting":true}'
```

Параметры: `offset`, `limit` (1..2000), `dryRun`, `maxPerRegion`,
`delayMs` (1000..15000), `enrichExisting`, `allowOwned`.

> Идти нужно **напрямую в backend**, а не через nginx: построение индекса
> каталога — это ~70 страниц по 1.7 МБ, около 5 минут, и оно упирается
> в 60-секундный таймаут прокси. Локально бэкенд открыт на 5001
> (`docker-compose.override.yml`); на сервере он наружу не смотрит, поэтому
> запрос делается изнутри docker-сети:
>
> ```bash
> docker run --rm --network onlyglamps_app-network curlimages/curl:latest \
>   -s -X POST http://backend:5000/api/admin/import/crawl/naturalist ...
> ```
>
> После первого прогона индекс кэшируется на 6 часов, и партии идут быстро.

## 6. Перенос на сервер дампом

Гонять краулер на проде необязательно: карточки можно набрать локально
и перенести бандлом, как это уже сделано для глэмпинги.рф.

```bash
# на локальной машине, после наполнения dev-базы
scripts/create-naturalist-dump.sh
# → deploy/imports/naturalist-draft-import-<stamp>.sql

# на сервере
scripts/import-naturalist-dump.sh deploy/imports/naturalist-draft-import-<stamp>.sql
```

Свойства бандла:

- ключ переноса — `SourceLinks.SourceUrl`, поэтому повторный накат
  не плодит дубли;
- недостающие регионы, города, типы и удобства создаются на приёмнике;
- **опубликованные объекты пропускаются** (`skipped_published` в отчёте) —
  накат не может затереть то, что уже живёт на сайте;
- `Slug` при коллизии с чужим объектом на приёмнике получает суффикс:
  нумерация slug'ов на сервере своя и с локальной не совпадает;
- всё идёт одной транзакцией, а `import-naturalist-dump.sh` перед накатом
  снимает полный `pg_dump` базы в `backups/`.

> Внимание: для НЕопубликованных объектов накат — это полная перезапись
> полей, фото, удобств и тарифов из бандла, а не дополнение. Это
> сознательно: источником истины считается локальная база, из которой
> собран дамп. Логика «заполнять только пустое» живёт в `EnrichAsync`
> и работает при обходе краулером, а не при накате дампа.

Ответ:

```json
{
  "found": 631, "imported": 5, "enriched": 1, "duplicates": 5,
  "skipped": 0, "errors": [],
  "samples": [...],
  "enrichedSamples": [
    { "objectId": 153, "writable": true,
      "filled": ["address", "coords"], "conflicts": [],
      "amenitiesAdded": 2, "photosAdded": 20 }
  ]
}
```
